# Internationalization (i18n)

How to use translations in the H-DCN portal. Source of truth for the full spec:
`.kiro/specs/Common/multi-language-support/requirements.md`.

## Core facts

- **Library**: react-i18next (frontend). Backend has its own translation maps
  (see "Backend" below).
- **8 locales**: `nl, en, de, fr, es, it, da, sv`. **Dutch (`nl`) is the default
  and fallback** and is the reference locale that must contain every key.
- **Admin panel stays Dutch-only** — do not translate Admin_Panel pages. The
  language selector is hidden there.
- **Never translate**: brand/proper nouns (`H-DCN`, `Harley-Davidson`) or
  user-generated/database content.

## Where translation files live (dual location — update BOTH)

```
frontend/src/locales/{locale}/{namespace}.json      ← source of truth (edit here)
frontend/public/locales/{locale}/{namespace}.json   ← runtime copy (HttpBackend loads this)
```

The app loads translations at runtime from `public/locales/` via HttpBackend, but
`src/locales/` is the authoritative copy. **Any change to a key MUST be made in
both `src/` and `public/` for all affected locales, in the same commit.** They are
required to be byte-identical — a property test enforces it
(`src/__tests__/i18n/localeSync.property.test.ts`).

Current namespaces: `common, dashboard, webshop, members, products, auth, events,
eventBooking, workflows`.

## Using translations in components

```tsx
import { useTranslation } from 'react-i18next';

function MyComponent() {
  const { t } = useTranslation('webshop'); // namespace per module
  return <Button>{t('cart.checkout')}</Button>;
}
```

- **Every** user-facing string on member-facing pages must use `t(...)` — never
  hardcode Dutch text. Categories to translate: headings, button/form labels,
  placeholders, validation + status messages, nav items, tooltips, modal titles,
  table headers, confirmation dialogs.
- **Interpolation**: `t('bulk.result', { succeeded, total })` →
  `"{{succeeded}} van {{total}} ..."`.
- **Plurals**: use i18next plural keys (`key` / `key_plural`) with `{ count }`.
- **Cross-namespace lookup**: `t('workflows:membership.fields.reason')` (prefix
  with `namespace:`).

## Translation key rules (ENFORCED by tests — Requirement 10)

These are hard rules, checked by `src/__tests__/i18n/translationFileConventions.test.ts`:

1. **Max nesting depth = 2.** Level 1 is a grouping key, level 2 is the string.
   - ✅ `{ "form": { "submit_label": "Opslaan" } }`
   - ❌ `{ "membership": { "confirm": { "approve": "..." } } }`  (depth 3)
2. **Key naming: lowercase snake_case / dot notation only** — pattern
   `^[a-z][a-z0-9_.]*[a-z0-9]$`. Start with a lowercase letter, use only
   lowercase alphanumerics, `_` and `.`, min length 2.
   - ✅ `submit_label`, `payment_received`, `reason_placeholder`
   - ❌ `paymentReceived`, `reasonPlaceholder` (camelCase), `Submit` (uppercase),
     `submit-label` (dash)
3. **JSON, UTF-8.** The Dutch (`nl`) file is the reference and must contain every
   key; each `nl` namespace must have at least one key.
4. **Empty string = missing** → triggers the Dutch fallback. Don't ship `""` as a
   real value.

> The `workflows` namespace currently violates rules 1 and 2 (camelCase +
> depth 3) and is flagged by the convention test. Per Requirement 10 the files
> should be conformed (rename to snake_case, flatten to depth 2, and update the
> `t(...)` calls in the ~9 consuming components). Do not add new violations.

## Adding or changing a key — checklist

1. Add the key to **`nl`** first (reference locale), in both `src/` and `public/`.
2. Add it to the other 7 locales (`en, de, fr, es, it, da, sv`) in both `src/`
   and `public/` — all in the same commit. (A real translation may come later,
   but the key must exist; missing keys warn in dev and fall back to `nl`.)
3. Keep depth ≤ 2 and snake_case (see rules above).
4. Reference it via `t('namespace:group.key')`.

That's 8 locales × 2 locations = keep them all in sync. When in doubt, run:
`npx react-scripts test --watchAll=false --testPathPattern="localeSync.property"`.

## Formatting (dates / numbers / currency) — Requirement 5

Use the `Intl` browser APIs with the active locale, never hand-rolled formatting:

- Dates: `Intl.DateTimeFormat` (short style for tables, long for detail/headings).
- Currency: `Intl.NumberFormat` with `EUR`, exactly 2 decimals, locale separators.
- Numbers: `Intl.NumberFormat` with the active locale.
- Null/undefined/unparseable value → render an empty string (no error text).

## Language resolution & preference — Requirements 2, 3

- Priority: **stored member preference → browser locale → Dutch**.
- Authenticated members: read/write `preferred_language` on the Member_Profile
  (Members table) via the existing update-member API.
- Browser detection matches the primary subtag (`en` from `en-US`); unknown →
  `nl`.
- Changing language applies within 1s, no page reload. If persistence fails,
  apply locally for the session and show a non-blocking notice.

## Backend (out of scope for react-i18next, but same locale set)

- **API errors** (Requirement 6): return a stable error key + a localized message
  based on the `Accept-Language` header (missing/unknown → `nl`). Translation
  files: `backend/layers/auth-layer/python/shared/i18n/`.
- **Emails** (Requirement 7): `Email_Renderer` selects template by the member's
  `preferred_language`; templates in `backend/email-templates/templates/{locale}/`;
  missing → Dutch.
- **Order PDFs** (Requirement 8): resolve language from the ordering member's
  `preferred_language`; translation maps in the backend shared layer; unknown/
  null → `nl`.

## Quick don'ts

- ❌ Don't hardcode Dutch strings in member-facing components.
- ❌ Don't edit only `src/locales` (or only `public/locales`) — update both.
- ❌ Don't add camelCase keys or depth-3 nesting.
- ❌ Don't translate the admin panel, brand names, or DB content.
- ❌ Don't format dates/currency manually — use `Intl` with the active locale.
